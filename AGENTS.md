# My Personal Balance

Self-hosted personal finance app: accounts, transactions, transfers, splits, tags, CSV/XLSX import, dashboards, and per-account tag prediction.

Read this file at the start of a new session, then the `AGENTS.md` in the service you are changing.

## Services

| Service | Path | Port | Role |
| --- | --- | --- | --- |
| Frontend | `frontend/` | 5173 | React SPA |
| Backend | `backend/` | 8000 | Auth, accounts, transactions, dashboard |
| Classifier | `classifier/` | 8001 | Train and predict tags |
| Postgres | compose service `db` | 5432 | Shared database `balance` |

Compose file: `compose.yml`. Containers: `balance-web`, `balance-api`, `balance-classifier`, `balance-db`.

The classifier reads the same Postgres database and the same JWT secret as the backend. It does not write tags; the frontend applies predictions through the backend.

## Run

```bash
kiri compose -f compose.yml up --build
kiri exec -it balance-api python -m app.scripts.seed
```

Backend startup runs `alembic upgrade head`, then uvicorn with reload. Frontend and classifier source are bind-mounted.

Local commands, without compose:

```bash
cd frontend && pnpm install && pnpm run dev
cd backend && uv sync && uv run alembic upgrade head && uv run uvicorn app.main:app --reload
cd classifier && uv sync && uv run uvicorn app.main:app --reload --port 8001
```

Use pnpm in `frontend/` and uv in the Python services. Commit `pnpm-lock.yaml` and both `pyproject.toml` and `uv.lock` together.

Both Python services run on Python 3.14 (`requires-python = ">=3.14"`, a `.python-version` in each service, `python:3.14-slim` images). uv picks the interpreter from `.python-version`; run `uv python install 3.14` once if it is missing. Keep pins exact, and keep packages the two services share at the same version.

## Frontend

Routes in `frontend/src/App.tsx`: `/login`, `/` (dashboard), `/accounts`, `/transactions`, `/classifier`, `/profile`. Everything except login sits behind `ProtectedRoute`.

- `src/api/client.ts` talks to `VITE_BALANCE_API_URL` (`http://localhost:8000/api`). The JWT is stored in `localStorage` under `token`.
- `src/api/classifierClient.ts` talks to `VITE_BALANCE_CLASSIFIER_URL` (`http://localhost:8001`) and attaches the same token.
- Server state uses TanStack Query. Shared types live in `src/types/index.ts`.
- Shared queries (`useAccounts`, `useTags`) and `invalidateTransactionQueries` live in `src/api/queries.ts`.
- UI primitives are shadcn/ui on Base UI (not Radix) under `src/components/ui/`, generated by the shadcn CLI. Do not edit them by hand. Prefer them over one-off controls.
- Layout follows the shadcn `dashboard-01` block: `src/components/app-shell.tsx` with a collapsible sidebar and site header.
- Theme is light, dark, or system via `src/components/theme-provider.tsx`, stored in `localStorage` under `theme`.
- Money helpers are in `src/lib/money.ts`. Sums are done in integer cents.
- Stack details and commands are in `frontend/AGENTS.md`.

Tests: `pnpm test` (Vitest). Every page has a test file under `frontend/tests/`. Pages that render money or take user input need a test. `pnpm run lint` and `pnpm run build` must pass too.

## Backend

Routers are mounted under `/api` in `backend/app/main.py`.

Auth is JWT (`python-jose`). Passwords are hashed with `bcrypt` directly (no passlib) in `app/core/security.py`; new passwords over 72 bytes are rejected with a 422. `get_current_user` scopes every query to the caller. Allowed currencies are `USD`, `EUR`, and `BRL` (`app/core/currency.py`).

Domain tables:

- `users` — name, email, password hash
- `accounts` — name, currency, user
- `tags` — label, user
- `account_import_mappings` — per-account CSV/XLSX column names
- `transactions` — date, description, amount, currency, optional tag
  - transfers: `is_transfer`, `transfer_group_id`, `transfer_direction` (`in`/`out`), `linked_account_id`
  - splits: `parent_transaction_id`

Import accepts CSV or XLSX. Required fields are date, description, and amount. Currency falls back to the account currency. Mapping is configured per account.

Migrations are in `backend/alembic/versions/`. Add a new revision for schema changes; do not edit applied revisions.

The backend has a pytest suite in `backend/tests/` (`cd backend && uv run pytest`). API tests use a `balance_test` database on the compose Postgres, created on first run. The classifier has a pytest suite in `classifier/tests/` (`cd classifier && uv run pytest`) that needs no database.

## Classifier

Training uses tagged, non-transfer transactions for one account. It needs at least 20 descriptions and 2 distinct tags. It fits TF-IDF character n-grams with logistic regression, complement naive Bayes, and a calibrated linear SVM, then keeps the best macro-F1 model. The frontend calls are in [`docs/api-map.md`](docs/api-map.md#classifier--classifierpage-via-classifierapi).

Models are joblib files at `{MODEL_DATA_DIR}/model_user_{user_id}_account_{account_id}.joblib`. That directory is gitignored.

## API map

Which page calls which route, every TanStack Query key, and what each write invalidates are in [`docs/api-map.md`](docs/api-map.md). Read it before changing frontend data flow or anything that crosses services.

The rule that breaks most often: after any transaction write, call `invalidateTransactionQueries` (`frontend/src/api/queries.ts`). It clears `["transactions"]`, `["transactions-analytics"]`, `["transactions-summary"]`, `["transactions-tag-trend"]`, `["accounts-balances"]`, and everything under `["dashboard"]`. The dashboard is anchored on the newest non-transfer transaction, not on today. `TransactionsPage` takes `from`, `to`, `tag_id`, and `account_id` from the URL.

## Conventions

- Keep HTTP handlers thin. New parsing, import, validation, and training logic goes in a service module (`backend/app/services/`, `classifier/app/services/`). `backend/app/api/transactions.py` predates this rule and still holds transfer, split, and import helpers. Do not add to them; when you change one, move it into a service.
- Scope data by `user_id`. A missing owned row is a 404.
- Amounts are `Numeric(12, 2)` in the API as strings on the frontend. Do not do money math with binary floats.
- Transfers are paired rows sharing `transfer_group_id`. All-accounts views must not double-count a pair.
- Splits are child rows pointing at `parent_transaction_id`.
- Behavior changes get a note under `specs/` in a `[specs]` commit. Older notes in that folder are background for the current code.
- Create every spec directly inside `specs/`, as a Markdown file with a unique, descriptive kebab-case name, such as `specs/import-preview-gating-unconfigured-mapping.md`. Do not reuse an existing spec's name; update that spec instead if it covers the same change.
- Implementation plans and task lists go in `tasks/<spec-name>/plan.md` and `tasks/<spec-name>/todo.md`, where `<spec-name>` is the spec's file name without `.md`. Each spec gets its own folder so parallel work never shares a file. `tasks/` is gitignored: never commit it, and never write a shared `tasks/plan.md` or `tasks/todo.md`.
- Do not open, search, or read `backups/`. It holds real database dumps with personal financial data. Exclude it from broad searches.

## Contributing

Every commit subject follows this pattern:

```text
[docs|specs|tech] <description>
```

| Prefix | Use for |
| --- | --- |
| `[docs]` | README, `AGENTS.md`, and other documentation |
| `[specs]` | Files under `specs/` |
| `[tech]` | Application code, tests, migrations, and dependency updates |

Rules:

- One prefix per commit. A spec and the code that implements it are separate commits.
- Description is imperative and specific: `[tech] dedupe transfer pairs on the dashboard`.
- No conventional-commit types such as `feat` or `fix`. The prefix above replaces them.
- Commit `pnpm-lock.yaml` with frontend dependency changes, and both `pyproject.toml` and `uv.lock` with Python dependency changes.
- Schema changes are a new file in `backend/alembic/versions/`. Do not edit an applied revision.
- Frontend changes that render financial data or handle user input need a Vitest test. Run `pnpm test` before a `[tech]` frontend commit.
- Do not commit `.env` files, secrets, or `classifier` `.joblib` models.

## Environment

Copy examples before a local run:

- `backend/.env.example` — `SECRET_KEY`, token lifetime, `DATABASE_URL`, `CORS_ORIGINS`
- `frontend/.env.example` — `VITE_BALANCE_API_URL`, `VITE_BALANCE_CLASSIFIER_URL`

Compose injects database URLs and the classifier CORS origin. The classifier reuses `backend/.env` for `SECRET_KEY`.
